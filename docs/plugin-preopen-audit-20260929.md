# 插件生态与预开源审计（2026-09-29 UTC）

## 结论与范围

当前工作台具备可用的插件开发能力，但还不是可以保证任意升级不破坏旧插件的成熟平台。`apiVersion: 1`、完整包批准和大量扩展点解决的是声明、准入与可扩展性；它们不能证明内部服务参数、调用语义、任意 DOM 选择器或第三方组合永远兼容。本轮补齐兼容前置检查、独立恢复进程、安全模式、明确适配及用户决定发送的修复草稿。

审查对象为本地待提交源码、插件导入/批准/激活/清理路径、宿主与界面扩展接口、测试与构建脚本、公开文档、依赖元数据及本地可达 Git 历史。其他窗口仍在开发的模型管理等变更不纳入本轮冻结验收或提交。没有发布、推送、部署、修改活动客户端或读取真实登录资料、聊天数据库及远端私有配置。

## 主要发现

| 等级 | 发现与影响 | 本轮处理 / 发布前要求 |

| 高，已修复 | 损坏偏好/清单与未完成激活缺乏完整恢复路径 | 保留损坏原文件、持久诊断、加载超时与迟到注册隔离；未完成激活后的重启进入安全模式 |

| 中，已修复 | 旧接口问题没有受限修复与人工接手入口 | 仅明确登记、调用语义相同的成员重命名可一键适配，并固定包摘要及适配内容。其他问题复制诊断/修复草稿，由用户进入安全模式、选择模型并发送 |
| 中，已补充 | 接口文档缺少自动变更门禁与故障恢复回归 | SDK 声明/宿主方法基线、Windows CI 配置、故障注入与旧插件回归。CI 尚未在远端执行，不把本机通过当作远端结果 |

## 已交付的恢复流程

1. 启动前建立诊断记录和独立恢复进程，再加载第三方插件。宿主或界面异步激活超时、异常退出、真实死循环、启动接口被挂起均有对应诊断；仅有阶段证据时显示“疑似相关”或“归因未知”，不伪造确定归因。
2. 兼容检查显示插件 ID/版本、工作台当前/上次版本、服务成员和所需/当前契约版本。旧插件未声明依赖时无法可靠推断所有失效接口；诊断明确不保证识别任意异常的根因。
3. “一键修复兼容问题”只应用已注册且摘要匹配的成员重命名适配，不改插件源码、不提高 apiVersion、不重批变化的代码包。按插件 ID/代码包摘要去重，逐个应用并重新激活；单项失败继续处理其余可修复插件，报告已适配、失败、无适配和剩余故障，不把部分成功宣称全部修复。批量等待时仍可安全重启；无适配或失败时提示进入安全模式。
4. “以安全模式重启”先持久化安全标记，再按进程创建身份核验并停止本工作台的进程树。不会按程序名称批量结束其他 Electron 或客户端。安全模式暂停全部导入工作台插件，保留插件配置、批准和启用偏好；内置功能及 Codex/Claude 原生插件不由此路径改动。
5. “复制诊断并准备 Agent 修复草稿”与普通复制相邻；只因用户点击才复制并保存草稿。进入安全模式后，新会话文本框收到可编辑草稿，不创建模型会话、不调用准备/翻译/提交、不自动发送或强制选择模型。正常新会话的模型偏好仍由用户控制。中文 UI 使用中文模板，其他 UI 语言使用英文模板；插件 ID、接口名与错误码不翻译。单份草稿汇总所有保留的未解决目标，要求逐项处理并报告已修复、未解决和未检查。诊断最多保留 50 项；复制每项前 2 个兼容细节并标注省略数，未运行及记录范围之外的插件不视为健康。实际 textarea 插入后按草稿 ID 确认，重载不重复插入；旧确认不能覆盖新草稿。

详细接口、权限、事件、错误与示例见 [文档 36](36-workbench-plugin-api.md)。菜单“插件诊断与安全模式”、快捷键 `Ctrl+Alt+Shift+P`、安全模式标记及手动 `--safe-mode` 均保留核心入口。恢复核心的专用路径不经过插件中间件；普通 `extensions.recovery` 服务可被扩展，但不能取消紧急入口。

## 公开树、历史与依赖审查

`npm run audit:public` 只读取 Git 跟踪文件与本地全部可达对象，不扫描用户配置。最终集成候选（基于 `46717ec`，排除其他未提交改动）709 个跟踪路径，提交前全部本地可达历史 2,017 个 blob（2,016 个文本 blob），无超出大小上限的对象；92 个工作树候选、222 个历史候选是正则命中数量，不是泄漏数量。定位到的类别包括合成测试用户名/私网地址、故意拒绝的密钥头、合成凭据样例、运行时模板路径和通用占位符；历史界面中的个人路径模式对应“你的用户名”占位符。自动扫描与有界人工核对未确认真实凭据泄漏，不能作为零泄漏证明。新增源码、最终发布树、标签、分发包与新历史仍需复查；没有重写历史或修改远端。

仓库图片 `docs/assets/model-control-reference.png` 为通用控件裁剪参考，未观察到账户或聊天信息；隐私检查不证明再分发授权。仅靠根目录没有敏感文件也不能认定 Git 历史安全。

本轮 `npm audit --json` 返回 0 个已知漏洞。锁文件的许可证元数据包括 MIT、ISC、BSD-2-Clause、BSD-3-Clause、Apache-2.0 和 `(MPL-2.0 OR Apache-2.0)`，没有未声明条目。该检查不是逐项法律审核、上游代码安全证明或安装包通知文件验收；本轮未引入外部参考项目代码，也未新增 npm 依赖。

## 维护要求与复验入口

每次新增/修改功能同时更新公开 API 和覆盖矩阵；改变服务参数或语义时按影响调整契约并提供可验证迁移，旧接口适配应有行为测试和撤销恢复测试。`node scripts/check-plugin-contracts.mjs --write` 是审阅后更新基线的工具，不是消除兼容错误的办法。注册扩展测试与真实产品任务分别计量。

- `npm run check:plugins`：导出的 SDK 声明与宿主路由名称漂移门禁，不能覆盖私有服务实现或 DOM 语义。
- `node --import tsx --test tests/plugin-*.test.ts tests/runtime-extensions.test.ts`：兼容、配置、失败清理、跨进程停止身份与修复草稿。
- `npm run test:plugin-recovery`：隔离 Electron 故障注入、独立恢复、安全重启、修复及草稿；输出只在忽略的 `build/qa/`。
- `node --import tsx scripts/test-plugin-extensibility.mjs`：现有多实例界面、设置页、配置重启与停用恢复回归。
- `npm run check:docs`、`npm run typecheck`、全仓单元测试和隔离生产参数构建：最终结果见 [本轮实现记录](16-implementation-status.md)。

本轮未做真实付费模型任务、DSH 版本对照、VPS 出网/部署、已签名安装包、macOS/Linux 桌面恢复验收；不据此声称这些范围通过。主进程启动前的操作系统、Electron 可执行文件或安装包损坏也不属于插件恢复进程可以完全兜底的范围。

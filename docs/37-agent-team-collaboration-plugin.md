# 37 · 内置协作插件：愿景与初步设计

状态：**未来方案，尚未开发**。记录及修订日期：2026-09-28 JST。

本次修订以“项目长期配置协作团队、用户决定何时新开团队会话”替代初稿的“单聊临时组队并解散”。不按每项任务自动新开会话；同一团队会话内可多轮交流，决策者按需要决定下属续用还是新开角色执行会话。同一模型可配置到多个身份，但身份上下文必须分开；补充双策划、并行工作区、验收合并、Git 提交和决策者复核的交付闭环。

本文件保存已经讨论的产品愿景和初步设计，供日后启动开发时使用。本轮仅落地文档，不创建插件包、不安装或启用示例、不改变现有会话行为、不调用模型。这里的拟议接口、交互和验收项都不代表已交付；实际实现与验证仍以 [文档 16](16-implementation-status.md) 为准。

## 1. 产品定位与已确定愿景

未来将这套能力实现为**工作台官方内置的项目协作插件**。一个项目可以配置一个或多个长期存在的团队／群聊，用户或受托 Agent 按用户意图配置身份及模型。用户像单聊一样选择继续现有团队会话，或新开一个全队上下文独立的会话，并和其中任意身份聊天。单聊也可负责讨论愿景、整理计划或发起委托，团队的决策者负责组织交付和最终汇报。任务结束不解散团队，也不强制关闭或重建会话。

名称建议使用“项目协作团队”，简称“协作团队”；“协作集团”保留为用户提出的候选名或团队自定义名称。团队总领在界面称“负责人（决策者）”，策划组也可显示为“讨论组”。下文采用“团队”作为暂定术语，不锁定最终产品名称。

“内置”指未来随工作台提供的第一方工作台插件，不是向 Codex / Claude Code 安装原生插件。它应使用与第三方插件相同的公开接口，不依赖只有内置代码才能使用的私有入口。第三方开发者应能扩展或替换角色策略、协作流程、上下文策略和界面。默认是否启用、最终名称及发布版本尚未决定。

| 已确定方向 | 预期体验 |
| --- | --- |
| 项目级群聊 | 左上角“新增会话／新对话”下方增加“群聊”入口；项目下可以配置一个或多个协作团队 |
| 用户控制团队会话 | 团队保留配置，用户选择新开或继续；新开时所有身份进入新的会话范围，不继承旧会话上下文 |
| 多轮对话与下属会话决策 | 用户可和任意身份多轮交流，通常先与决策者讨论；决策者按需为下属续用或新开执行会话 |
| 角色和模型 | 决策、策划、执行、验收分别配置；同一组可有多个模型，同一模型可绑定多个身份但不共用身份上下文 |
| 身份组共享 | 同组成员至少能访问同一份组内工作记录和已确认结论，不各自持有互不相通的资料 |
| 多种上下文策略 | 支持成员独立、全群共享、身份组共享；默认协作设计采用身份组共享 |
| 运行总控台 | 看见每个成员所属组、当前任务和真实状态；消息传递有动画及方向箭头 |
| 单聊向团队委托 | 单聊先讨论愿景／计划，用户明确委托后由 Agent 把任务交给本项目指定团队的负责人 |
| 项目团队配置 | 用户预先配置，或让 Agent 按意图配齐各身份；已有团队后续复用，不每次任务都重新组建 |
| 完整交付闭环 | 双策划互审达成共识，执行组独立工作区实现，验收组合并及提交，决策者逐项核对目标并按来源汇报 |
| 插件化实现 | 界面、组队策略和协作服务都可继续扩展；停用后恢复普通工作台入口 |

以上是产品目标，不把“接口能够承载”写成“完整团队功能已经实现”。原有示例插件继续只供开发文档和隔离测试使用；本方案不授权安装它们。

## 2. 项目、团队与任务入口

### 2.1 长期团队与用户控制的新会话

建议的归属层级为：**项目 → 一个或多个协作团队／群聊 → 用户创建的团队会话 → 多轮讨论、任务与返工轮次**。一个团队会话可以承载连续讨论和多个任务，任务与会话不是一对一关系。初版可把一个团队对应为一个群聊入口，具体导航形态待交互设计确认。

- 团队保存负责人、身份组、模型席位、思考档位选择策略及项目关联，不等于永远复用同一个模型线程。
- 用户可以预先配置团队，也可以明确让 Agent 为项目创建或调整团队。配置完成后保留并回读；打开、选择或保存配置本身不启动任务。
- **是否新开团队会话由用户决定。** 点击“新会话”后，全队所有身份都进入新的会话范围；可先选择一个身份聊天。其他身份首次被用到时再建立实际执行线程，不为了新建会话把全队模型都调用一遍。
- 新会话不复制旧会话的讨论、草稿、消息收件箱、工具结果或原生隐藏状态，只装入本次输入、角色说明及显式选定的项目资料。旧会话保留可回看；在途任务仍属于旧会话，新建本身不表示取消它们。
- **新任务不等于新会话。** 用户继续在当前会话发布任务、补充要求或讨论时，保持当前对话，不能因消息里出现新任务就自动切换全队上下文。
- 用户可以连续和决策者聊多轮，也可选择其他身份。一个身份组有多个模型时，应显示实际收件席位／组范围，避免把定向聊天无提示地广播给全组；切换聊天对象不意味着重置任何身份。
- 同项目多个团队可分别负责不同方向。委托使用明确团队和负责人 ID；名称相同或存在多个候选时不能随意广播。存在用户已配置的默认团队时可直接采用并显示目标。
- 任务启动时冻结团队配置修订。以后修改团队默认模型，不悄悄更换正在执行的身份会话；任务内调整需要明确记录交接和影响。

“干净上下文”针对用户明确新开的团队会话，以及被明确新开的角色执行会话；继续现有会话保留上下文本来就是预期行为。隔离指工作台输入和运行状态的隔离，不是仅清空画面，也不是对模型训练知识的承诺。项目规则、必要文件和用户选定的长期知识可以明确纳入，界面应显示本次导入了什么。

### 2.2 决策者管理下属的执行会话

在同一个团队会话内，用户与决策者的多轮讨论可以持续。决策者根据任务关联、已有有效上下文、角色切换或上下文混杂情况，决定策划、执行、验收等下属继续原有角色会话，还是建立新的角色执行会话；用户明确指定的做法优先。

这是已配置职责中的常规协调决定，不要求每次新开下属会话都向用户重复确认。但必须记录选择、原因及提供给新会话的任务包，能在总控台查看；不允许静默清空用户正在直接聊天的身份会话。下属存在在途执行时，先核对完成或取消回执，再决定后继会话，不借新开会话重复提交结果未知的任务。

仅为某个下属新开执行会话，不等于新开整个团队会话：决策者及其他身份继续原会话，组公共日志和成果保留。新下属会话从明确选择的当前任务包、组快照或资料引用开始，不隐式复制被隔离的完整旧执行历史。全队同时进入新会话仍由用户的新会话动作或明确指令控制。

### 2.3 单聊讨论后交给负责人

1. 用户先在普通单聊中讨论大型任务的愿景、取舍或计划，原会话的历史和绑定保持不变。
2. 用户明确要求交给本项目团队后，发起 Agent 确定团队及负责人；若用户同时授权配置团队且尚无合适团队，先创建可复用的项目配置。
3. Agent 整理任务交接包：原始目标、已确认约束、验收标准、选定方案、未决问题、相关资料引用、用户授权范围和报告接收方。讨论中的猜测不包装为用户决定，关键逐字要求与原文引用保留。
4. 将交接包发到用户选定或已配置接收的团队会话，创建或关联任务记录；不因为这是新的任务就自动新开团队会话。只有用户要求新开时才创建新的团队会话。负责人接收并回读任务版本，再开始本次已授权的交付流程；普通咨询或只发送参考消息不启动任务。
5. 团队负责人独立承担后续协调，发起 Agent 不必一直充当总控。结束后向发起 Agent 发送带证据的结果，同时在团队任务和原会话关联入口中保存结果。

交接默认发送可核查的任务包和选定资料，不自动复制整个单聊历史。原单聊和团队任务通过来源与回报关系关联，不合并为同一上下文。已经明确要求“交给团队执行”的有效委托不应再按每个成员或阶段重复询问。

### 2.4 用户直接与团队身份交流

用户可以在当前或自行新建的团队会话里，选择任意身份开始聊天，通常先和负责人反复讨论愿景及计划，再交付执行。每条讨论消息不是一次新的任务启动；直接发布的任务与 Agent 委托使用同一接收及验收流程。报告路由不同：直接发布则向用户汇报，由单聊 Agent 委托则向该 Agent 汇报。来源和接收目标由宿主绑定，不能由模型自行冒填；无效或已删除的来源应明确提示并保留可供用户阅读的结果。

发起 Agent 已结束当前回合时，报告仍可持久投递和显示通知；是否进入它的后续模型输入遵循原生会话及用户任务授权，不把“报告已送达”冒充“对方已阅读”。团队本身的已授权任务生命周期不依赖原单聊请求一直存活。

工具接入仍遵循实际运行时生命周期：插件提前加载时可以在当前任务中调用；任务开始后才启用，不保证热插入正在执行的请求，也不能为加载工具自动重发旧任务。

## 3. 角色、成员与执行方式

### 3.1 初始角色模板

| 身份组 | 职责建议 | 主要输出 |
| --- | --- | --- |
| 决策者／负责人 | 接收任务、核对目标、组织推进，最终逐项复核并向来源汇报 | 目标清单、已确认决策、返工意见、最终报告 |
| 策划／讨论组 | 默认两个策划席位，独立提出方案后互相挑刺，形成双方认可的详细计划 | 方案修订、双方评审、任务分解、依赖与验收条件 |
| 执行组 | 多个成员领取任务，在各自工作区实现并提供可核查结果 | 变更、产物、执行记录与阻塞说明 |
| 验收组 | 由适合审查的强模型复查结果、处理整合及验证，符合条件时提交 Git | 评审、集成结果、测试证据、提交标识、完成情况报告 |

这些角色是可编辑配置，不是固定四个 Agent。每个身份组可配置多个模型席位。角色说明、任务授权和实际执行权限分别保存；“决策者”等名称不增加设备或系统权限。模型能够读取自己的身份和当前任务，界面中文与发给模型的英文工具说明分别维护。

### 3.2 同一模型、多种身份、独立上下文

用户所说“一个模型担任多个身份”表示**模型目标可复用，不同身份之间不共用原生会话**。例如同一型号同时配置为决策者和验收者时，要建立两个角色席位；在当前团队会话中，它们各有原生线程、角色说明、消息和上下文游标。一个身份自己的线程可跨多轮讨论及相关任务继续，或按用户／决策者的明确决定新开。

同组多个成员共享当前团队会话的组工作记录，按任务提取需要的内容；跨组只通过明确发布的计划、任务包、产物和报告沟通。不能因为使用同一模型就让验收身份继承决策身份的全部讨论，也不能把内部思考作为共享记录。独立上下文可减少直接的角色串扰，但不据此宣称同型号复核具有完全独立的判断能力。

### 3.3 未指定模型时的配置策略

用户指定的模型、身份、运行时和思考深度优先。未指定部分由受托 Agent 从**实际可用的模型目录**中选择，并将选择及理由保存为团队配置：

- **决策者**优先适合复杂推理、目标核查和统筹的最强可用候选。
- **策划组**通常配置两位强推理模型，优先 Claude 与 Codex 使用路径各一席，形成互相质疑和补充的方案。两席须针对同一版方案分别作出明确评审。
- **执行组**优先工具使用、代码实现和任务执行能力强的候选，可配置多个席位并行领取任务。
- **验收组**优先审查细致、理解项目和整合改动能力强的候选，可配置多个强模型复查。
- **思考深度**由 Agent 按任务及实际支持档位选择；未指定时，决策和策划作为“大脑”通常优先极高或该模型支持的最高合适档位。执行和验收按需要选择，不把 `ultra`、`xhigh` 等字符串强塞给不支持的协议。

“当前最强”是每次配置时的选择目标，不是写死某个型号，也不按名称、价格或上下文长度单项排序。目录提供可用性及已知能力，角色偏好还应结合用户偏好、版本化的能力资料和已有可信验证；证据不足时记录选择依据与不确定性，不伪造能力排名，也不擅自启动付费模型测评。

Claude／Codex 在上述偏好中代表用户熟悉的两条使用路径。落实配置时必须记录实际运行时、模型提供方、型号及参数，不能把运行时名称当成模型名；用户指定模型厂商组合时按明确目标执行。期望的一方不可用时，标明配置差异，不能静默宣称已满足双路径配置。

自动选择发生在用户授权的团队配置或明确调整时；目录变化不会偷偷替换运行中的成员。配置版本、实际型号、思考档位和能力缺失均可查看、修改及回读。

### 3.4 两种执行方式

- **原生子 Agent**：使用实际运行时已支持、已探测的原生创建和协作能力；数量、层级、模型选择及生命周期遵循原生行为。插件不把自己的分组设置冒充原生配置。
- **插件管理的成员会话**：由插件组织独立会话，绑定可用模型目标，适合跨模型、跨来源及注册式第三运行时协作。组关系、消息路由和共享上下文属于插件业务逻辑。

两种方式可以在总控台统一展示，但必须保留来源标记和不同能力。运行时、模型提供方、执行位置、网络出口独立建模。不能按模型名称猜运行时，也不能把插件成员会话描述成厂商内部原生线程。

成员数量不设置额外的固定“每队一个”上限。任务可提供用户明确选择的用量或并发策略，不能覆盖原生硬约束，不能把当前开发会话暂停子 Agent 委派的规则误写成产品限制。

## 4. 从计划到交付的完整闭环

### 4.1 阶段与通过条件

| 阶段 | 工作与输出 | 转入下一阶段的条件 |
| --- | --- | --- |
| 接收任务 | 决策者根据交接包或用户输入建立逐项目标、范围和验收清单 | 任务与来源可追溯，必要输入齐备 |
| 双策划讨论 | 两席提出方案、相互挑刺、回应问题，修订到可执行的共同方案 | 两席明确认可同一方案版本；阻塞性异议已处理 |
| 任务拆分 | 将方案拆成带责任、依赖、工作区、产物和验收要求的详细任务 | 每项任务可追溯到原始目标，职责及依赖清晰 |
| 并行实现 | 执行组领取各自任务，在独立工作区完成实现和必要验证 | 交付确切产物／变更及证据，未完成和未知项明示 |
| 验收与整合 | 验收组复查各项成果、处理冲突、合并并对最终整合状态复测 | 评审和集成验证通过；证据对应实际整合版本 |
| Git 提交 | 项目已有 Git 时，按项目规则提交本任务核对过的变更 | 暂存范围正确、无敏感资料及他人未完成改动，记录提交标识 |
| 决策者终审 | 将验收报告、产物和提交逐项对照最初目标 | 所有必需目标都有相符证据，关键异议和失败项已解决 |
| 按来源汇报 | 直接向用户或委托 Agent 发送结果、证据及限制 | 报告记录和投递可回读；投递不等于对方已读 |

策划共识不是“讨论了一定次数”、多数投票或仅一席宣称双方同意。每次认可绑定方案修订；实质变更后，旧认可不再自动有效。分歧不能靠复制对方回复、隐藏异议或无限发送“继续”消失；需要新证据、新方案或清晰的待决事项。无法收敛时保持阻塞并说明原因，而不是伪造共识。

### 4.2 独立工作区与验收合并

- 每个执行任务记录起始版本、负责范围、依赖和产物。支持 Git 的项目优先使用独立工作树／分支；没有 Git 时设计独立任务目录和显式整合步骤，不擅自初始化 Git。
- 领取任务使用可核对的任务记录和幂等操作，避免重连后重复执行。不同执行者不直接并发写同一集成工作区。
- 验收组可以并行评审，但合并到目标版本和提交需要串行的集成责任及版本校验。提交完成不能替代测试，单分支测试也不能代替合并后的验证。
- 评审包包含修改范围、起始版本、产物引用、已跑验证、失败／未验证项和依赖；无证据的“已完成”不作为通过依据。
- 只整合并提交本任务已经核对的修改，保留用户及其他团队的工作；按现有仓库规则组织本地提交，不自动推送、发布或部署。无 Git 的任务提供产物和验证清单，不虚构提交哈希。

### 4.3 决策复核与返工

验收组先把完成情况交给决策者，由决策者对照最初的目标清单逐项核查，而不只概括验收组的结论。发现遗漏、方向偏离、质量问题或证据不符时，将明确问题和受影响目标交回策划／讨论组，进入“修订方案 → 重新分派相关任务 → 验收整合 → 决策终审”的下一轮。

返工保留本任务的讨论和证据，用新轮次及修订关联前一轮；不把未受影响的已通过任务全部重做，也不把返工当作新的无关任务导入其他任务上下文。提交后需要修正时追加可审查的修复提交，不自动重写已有历史。只有决策者确认目标满足后才形成最终完成报告；预算耗尽、用户停止、运行时失败或无法收敛均有独立状态，不能标成圆满完成。

这个流程由用户已经启动的任务及明确阶段转换驱动，可以按任务授权继续必要的讨论与返工；普通 peer 消息不等于新任务授权。不得实现外层无限续投、限流后自动重启／换账号或没有进展的重复调用。实际调度、停滞判定、恢复和用量策略仍待开发及验收。

## 5. 上下文设计

### 5.1 三种逻辑策略

| 策略 | 共享范围 | 使用建议 |
| --- | --- | --- |
| 成员独立 | 每个成员有独立历史，通过显式消息或产物交流 | 独立审查、彼此隔离的子任务 |
| 全群共享 | 成员读取当前团队会话的公共记录，角色执行会话仍分别存在 | 小团队、需要共同跟进的讨论；不跨入其他团队会话 |
| 身份组共享 | 当前团队会话的全群共识加本组工作记录；按任务标记和筛选，跨组通过消息及发布的结论同步 | 默认大型任务协作模式 |

这里“独立”按团队会话及角色席位划分，不按模型名称划分。相同模型在决策与验收身份下必须独立；更换模型不应该丢失当前会话对应组的公共记录。同一团队会话中的任务可以延续用户选择保留的上下文；用户新开团队会话时三种策略都不能自动继承旧会话聊天，也不能取消同型号跨角色的原生会话隔离。

**身份组共享是核心要求。** 采用该模式时，同组成员必须能读取同一份有版本的组公共日志；上下文窗口较小的成员可以得到摘要和原文索引，但不能默默变成孤立会话。各成员的运行时会话、工具执行状态和未公开的内部推理仍然独立。

### 5.2 推荐的三层结构与会话范围

1. **当前团队会话的全群层**：用户目标、授权范围、选定项目资料、共同约束、已确认决策和跨组交付；具体目标及验收条件关联任务记录。
2. **当前团队会话的身份组层**：本组公开讨论、计划、资料引用、可共享工具结果和阶段结论；采用统一追加日志及修订版本，并保留任务标记。
3. **角色执行会话层**：具体分派任务、执行分支、已读取上下文版本、未公开工作进度及原生线程引用；可继续或按明确决定建立后继会话。

所有层都绑定 `projectId`、`teamId` 和 `conversationId`；任务内容另带 `taskId`，角色执行再绑定 `roleSlotId` 和 `roleSessionId`。缓存、游标和收件箱不能仅以模型名索引。团队配置可复用，角色运行上下文由“团队会话 × 角色席位 × 执行会话代次”标识，不因新任务自动重建。策划成员共享当前会话的策划组工作记录，各自执行线程及初始意见仍可分别保留。

用户新开团队会话时为全队建立新的角色会话范围，实际调用时使用新原生线程；决策者单独新开下属时只创建该角色的新代次。不通过清空 UI 后继续旧线程伪装隔离。若未来采用运行时重置能力，必须验证服务端历史、附件引用、挂起消息和任务状态确已重置。跨团队会话复用知识采用显式选择的项目资料快照或已确认知识条目，并显示来源；旧讨论不自动提升为项目知识。

组共享由规范记录驱动，不是把多个模型强行放进同一个原生会话对象。成员提交公开结果后追加组日志，其他成员在其运行时支持的输入时机读取新增内容。模型正在执行时看到的是本次请求的快照，不能声称它已经自动获知之后写入的全部记录。

### 5.3 版本、同步与长任务

- 为团队、组、消息和任务使用稳定 ID；日志有递增序号、来源及时间。维护组当前版本和成员已接收版本，必要时另存成员显式确认版本。
- 派发任务时冻结相关上下文版本；新成员通过快照加增量加入，旧成员按游标补齐。重试不重复追加同一消息，不把旧历史每轮作为“新消息”再次注入。
- 总控台区分“可读取”“已注入原生输入”“成员明确确认”三种证据。差距可显示为待同步版本数，不能把传输回执当作理解证明。
- 共享资料保留原文与来源；阶段摘要注明覆盖范围、生成者和版本，允许按需取回原文。摘要不宣称无损压缩。
- 共享结论采用修订比较或显式决策事件，避免并发成员互相覆盖。基于过期版本提交的关键决策应提示冲突或重新核对。
- 长文件和大型工具输出按引用、分页与按需读取提供。对保有历史的原生会话做增量同步；无状态请求仍需构造完整的所需输入，不能只发送增量却假定服务器保存了历史。
- 原有 `onContext` 只能贡献有限长度的参考字符串，不能直接充当无限组日志。正式开发时需要专门的读取工具、内容投影和回执协议，并验证各执行路径的注入位置。

## 6. token 与缓存目标

目标是在满足沟通和可追溯性的前提下，减少重复材料、无效往返和不必要的模型调用；**逻辑上下文共享与服务商计算缓存复用分别验收**。

初步策略如下，均需在实际提供方和模型上验证效果：

- 尽可能稳定公共指令、工具定义、组资料的序列化顺序，将变化内容组织在适合该协议的位置；不是简单把全组全部历史重复拼接到每条请求。
- 对长任务采用增量同步、按需取材和带来源的阶段摘要。全文重复发送、摘要生成和额外协调都有成本，应比较总用量而不只看命中率。
- 缓存配置按实际运行时／提供方／模型能力适配；不承诺跨模型、跨厂商、跨账号共用 KV 缓存，也不把一个缓存标识当作通用共享会话句柄。
- 复用已公开的会话用量回执，按成员、组、运行时和模型展示输入、输出、缓存读写及缺失数据。聚合时去重，避免把包含子任务的原生汇总再与子任务用量相加。
- 未上报缓存数据就显示未知；组共享成功不等于缓存命中，缓存命中也不等于全部输入只计费一次。未掌握有效价格时，不显示推算出来的实际账单节省金额。

本文不冻结厂商缓存参数、门槛、时长或价格。正式实现适配时，重新核查官方文档，在 [研究来源](07-research-sources.md) 记录版本和证据，并进行经过授权的真实模型对比测试。

## 7. 可视化总控台

### 7.1 信息布局

- 顶部提供项目、团队及团队会话切换，保留明确的“新会话”入口与聊天身份选择；可继续当前对话，不由任务数量自动切换。另显示任务目标、当前轮次、整体阶段、阻塞和结束状态，以及能力确实支持的停止／恢复操作。
- 主区域按身份组排列节点；每个成员显示角色、模型来源、任务摘要、真实运行状态及上下文同步情况。
- 箭头展示任务分派、组内交流、跨组交付、验收返工和结果汇总的方向；消息传输可有光点或流动动画。
- 点击成员打开公开会话和已收到的工具记录；点击箭头打开对应消息、来源、时间与投递状态。
- 侧边或底部保留事件时间线，可按组、成员和消息类型筛选；回放模式明确区别于实时模式。

展示节点的默认关系为“用户／委托 Agent → 团队负责人 → 双策划讨论 → 多执行成员 → 验收整合与提交 → 决策终审 → 用户／委托 Agent”。策划席位之间画双向讨论箭头，终审不通过指回策划组；相关任务的返工去向和轮次明确。团队配置视图与具体任务运行图分开；同一模型的不同身份显示为不同节点，不能合并它们的状态或上下文。

### 7.2 动画的真实含义

动画必须来自可追溯事件，不能为了显得繁忙而虚构通信。任务状态与消息投递状态分别建模：

| 观察到的事实 | 可显示的状态 | 不可据此推断 |
| --- | --- | --- |
| 已进入持久消息日志 | 已排队／已记录 | 对方已经收到或开始处理 |
| 原生输入接受回执 | 已投递 | 模型已读懂、赞同或完成 |
| 插件定义的成员确认事件 | 已确认接收指定消息／版本 | 整个任务已经通过验收 |
| 实际执行状态或完成通知 | 运行中、等待、完成、失败等 | 没有观察到的内部步骤与隐藏思考 |
| 连接中断或回执不明 | 结果未知／待核对 | 已失败且可以安全重新提交 |

同一事件只有一个稳定身份；重复通知不重复播放“新消息”。页面重开先读取快照，再从日志游标补齐，不把 `onEvent` 的瞬时通知当作可靠持久队列。记录可以按序回放；跨成员的到达顺序不能冒充不可观测的精确执行先后。

提供减少动画选项和键盘可访问的消息列表；浅色、深色、窄窗口均可读。颜色不是唯一状态标记，大团队使用聚合视图和按需展开，避免大量动画影响工作台运行。

## 8. 初步模块与数据模型

以下是职责划分建议，不是已创建的目录或类型：

| 模块 | 责任 |
| --- | --- |
| 团队配置服务 | 项目关联、持久团队／身份／模型席位、选模策略、配置修订 |
| 会话服务 | 用户控制的团队会话、身份聊天选择、决策者控制的下属执行会话代次及历史关联 |
| 任务与委托服务 | 既有团队会话中的任务记录、任务包、来源及报告路由、任务授权与生命周期 |
| 协作编排 | 双策划共识、任务依赖与领取、结果收集、验收整合、终审及返工 |
| 上下文服务 | 团队会话及角色隔离、任务标记和投影、组公共日志、快照、修订、成员游标、摘要及材料引用 |
| 消息与事件服务 | 定向消息、幂等、投递回执、事件序号、重连补齐 |
| 运行时连接 | 复用宿主原生能力或注册式适配器，将真实状态映射到成员 |
| 总控台 renderer | 群聊入口、组和成员视图、箭头动画、详情与回放 |
| 用量聚合 | 使用已有计量证据，按团队维度去重汇总，明确未知值 |

拟议实体：

| 实体 | 最少需记录的信息 |
| --- | --- |
| Team | `id`、`projectId`、名称、负责人席位、角色配置、默认上下文／选模策略、配置修订 |
| RoleGroup / RoleSlot | 团队、职责、席位集合；每个席位的模型目标、思考策略和配置来源，模板不夹带原生聊天状态 |
| TeamConversation | `id`、团队、用户的新建依据、标题、选定资料、当前聊天身份、会话状态；可含多个任务及多轮讨论 |
| Task | `id`、`conversationId`、任务说明、来源类型／来源会话、报告路由、任务授权与状态；创建不重置团队会话 |
| TaskRun | `id`、`taskId`、配置快照、执行／返工轮次、方案修订、阶段、状态及终审结果 |
| RoleSession | 团队会话、角色席位、代次、原生线程引用、续用／新建决定及来源、关联前一会话、上下文游标 |
| MemberRun | 本次任务运行、角色席位和 `roleSessionId`、实际模型／运行时参数、能力与状态；同一角色会话的在途请求须协调 |
| PlanRevision | 任务／轮次、方案、目标映射、双方独立评审、阻塞异议和认可版本 |
| Assignment | `id`、责任成员／组、任务、依赖、领取记录、输入版本、起始版本／工作区、产物、验证与结束状态 |
| Review / Integration | 对应产物和集成版本、评审结论、冲突处理、复测证据、Git 提交及逐项目标核对 |
| ContextRecord | 项目／团队／会话／组或角色范围、任务标记、序号、来源、公开内容或材料引用、摘要覆盖范围、修订 |
| TeamMessage | `id`、来源绑定、接收成员／组、关联任务和轮次、正文引用、幂等键、投递及确认回执 |
| TeamEvent | `id`、团队与任务内序号、事件类型、来源、对象及关联事件、时间、可回放载荷 |

团队配置、模型目标、团队会话、角色执行会话和任务状态分开保存。任务结束只结束该任务运行，用户仍可在当前团队会话继续聊天或发布任务，也可自行新开会话。插件停用或升级不删除历史；恢复需要核对真实运行状态，不能只凭存档中的 `running` 自动重启模型。

| `team/role-sessions/renew` | 当前团队会话、绑定决策者或用户来源、目标下属、原因及输入快照 → 该角色的新代次；核对在途状态，不重置其他身份 |
| `team/tasks/create` | 已选团队会话、任务包、选定资料及真实来源 → 任务记录和报告路由，不默认新建团队会话 |
| `team/tasks/start` | 任务 ID、期望修订、有效任务授权、幂等键 → 使用配置快照的协作运行标识 |
| `team/plans/propose`、`team/plans/review` | 方案版本、绑定策划身份、评审结论及问题 → 新修订或该版本的共识状态 |
| `team/tasks/assign`、`team/tasks/claim` | 运行、责任席位、依赖、上下文及工作区版本、幂等键 → 可核对的分派／领取记录 |
| `team/context/read` | 绑定团队会话、角色会话及可选任务过滤、范围、游标及预算 → 快照／增量、下一游标和截断说明 |
| `team/context/publish` | 绑定团队会话与来源、任务标记、内容／引用、期望修订、幂等键 → 新版本和记录 ID |
| `team/messages/send` | 绑定发送者、收件对象、内容、任务／轮次、幂等键 → 已记录消息及投递状态，不独自构成新任务授权 |
| `team/reviews/record` | 验收身份、产物／集成版本、评审、测试与提交证据 → 可供终审核对的验收记录 |
| `team/tasks/return`、`team/tasks/complete` | 决策身份、目标核对及依据、期望修订 → 下一返工轮次或最终报告记录 |
| `team/snapshot`、`team/events/read` | 团队、任务过滤和可选事件游标 → 当前状态或可补齐的事件页 |
| `team/tasks/stop`、`team/tasks/reconcile` | 任务、期望修订和相应依据 → 已确认状态、仍运行成员与待处理项；不删除团队配置 |

建议事件覆盖配置更新、用户新建团队会话、角色会话续用／新建决定、新任务、双策划评审及共识、任务分派／领取、运行状态、消息记录／投递／确认、上下文更新、验收／提交、决策返工及任务完成。具体英文事件名、错误码、分页、容量和兼容版本留到接口设计阶段冻结。至少区分授权不足、版本冲突、团队会话／角色范围错误、目标不可用、运行时不支持、投递未知和存储失败。

正式实现时，为每项契约补齐参数、返回、权限、错误、事件、生命周期、迁移与测试，并同步更新文档 36。若发现公共接口缺口，应补齐实际路径后验收，不能仅依靠全信任 Node 访问或把缺口记入本文宣称完成。

## 10. 启停、授权与数据保存

- 启用插件、打开群聊页面、查看总控台和选择模型本身不发起模型任务。任务授权需绑定用户目标和作用范围；角色说明、他人消息及模型自己生成的内容不构成新授权。
- 复用现有原生任务执行，不添加外层无限“继续”、限流后自动重启、切账号或普通 peer 消息触发新回合。一次合法团队任务中的委派不要求重复询问已经授权的同一事项。
- 任务停止首先停止该任务的新派发，再请求各运行时支持的取消；只有得到回执才标记成员已停止。不支持暂停／恢复的运行时不能展示假按钮；结果未知进入核对状态。停止某项任务不删除团队，也不误停其他任务。
- 插件停用或更新时清理自有 UI、监听和注册接口，同时保留任务与数据。仍在运行的原生成员按可验证生命周期处理，不能认为撤下界面已撤销外部动作。
- 插件包、偏好、团队历史和模型凭据分别保存。非敏感的小型设置可使用插件存储；对话和产物写入专用用户数据区域，凭据沿用宿主秘密存储，不放入配置或上下文。
- 代码 ZIP 导出不包含群聊、成员原文、用户路径、凭据和运行证据。公开文档只用合成示例；本文件不复制私人对话或设备信息。
- 开发与测试可在独立临时数据目录导入测试包；不因此安装到实际用户工作台。正式“内置分发”的启用与更新方式需在发布设计阶段明确。

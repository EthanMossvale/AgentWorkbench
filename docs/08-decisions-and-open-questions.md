## 2. 建议采用的架构决策

### A01 · 产品层与原生内核分离

我们拥有窗口、会话列表、账号元数据、设备授权、本机工具桥；原生 CLI 拥有认证、模型循环、原生历史与上下文。不要重复开发一套看似原生的 loop。

替代方案“先自研完整 harness”不用于首期。后续接入其他模型时，可独立评估成熟开源 harness，而非把任意第三方模型强行包装成两家原生 CLI。

### A02 · H 是首期目标，不静默换路线

H = 远端原生 CLI / 原生登录 + 本机执行 + 远端模型请求，是首个原生执行模式。独立翻译是它之前的交付，不依赖SSH，不能被解读为改做本地CLI/SDK登录。

E = 本地 CLI + 远端网络出口，只保留为概念对照，不列首期实验/交付。若 H 暂无可接受实现，报告缺口并继续研究或向用户说明，不自动改做 E、SDK 或 MCP 降级版。

### A03 · 保留工具契约，逐项证明“手脚”

先找原生支持的执行宿主/协议边界，再决定桥接层形态。不能只给远端模型加一两个自定义工具就说保留完整原生体验。

Codex 已有 `exec-server / deferred executor` 这一实际入口，应从已实现代码与历史通过用例出发。不要因为最新文档采用不同名字就把已有成果抹去，也不要用原生 UI 子窗口的验收代替原生工具证据。

Native parity 不是必须零适配代码；本机桥本来就是要建设的模块。关键是每个原生能力的模型可见契约、权限、执行语义、错误、取消和恢复是否保真，并如实标记缺口。

### A04 · 会话绑定与切换

MVP 绑定 provider/runtime/account/execution/egress。原生允许的同家模型/effort 调整可放回合边界；跨家建立有来源、有损提示的新会话。无损切换暂不承诺。

### A05 · 每设备授权而非共享管理员私钥

管理员分发受管 workspace 权限；设备自己持有私钥。相同所有者可多设备访问一个 workspace；不同所有者默认隔离。平台权限由服务端校验。

管理流先发现/接管，后按差异补齐；已有用户不是必须替换的历史包袱。支持明确的删除重建流程，但不能把它作为发现失败或连接超时的自动动作。私钥与公钥授权的发现范围分开，见 [专门设计](11-workspace-discovery.md)。

### A06 · 拒绝能力幻觉

能力列表来自协议版本、探测和实测。没有额度接口就显示未知；没有 Fast 就禁用；上下文数值不能超越真实模型上限；UI 不能伪造设置生效。

### A07 · 环境投影与文件访问分离

SSH只读采集允许的VPS字段，自动生成版本化profile；环境查询返回该视图，缺失/过期不补扫宿主。实际工具能力、执行位置、文件内容和命令结果不被伪造。强隔离、投影和host-exposed分别标注。

文件面owner-wide，同owner普通跨目录工作不加workspace围栏；设备盘点、其他租户和管理员控制面仍是独立边界。文件自身包含主机信息时不暗改；详见 [14](14-environment-projection.md)。

### A08 · 翻译是闸门与显示层，不是协议改写代理

保留中文原稿、实际提交英文及原生输出；中文译文不回灌会话，不触发工具，不改签名/审批/环境来源。第三方翻译账号/effort/费用单独配置。输入翻译失败暂停发送，输出失败只重译；详见 [13](13-translation-module.md)。

## 4. 后续讨论点（本轮不因此停工）

1. 最终名字与定位：个人工具、团队工具或面向公众产品。
2. 同一用户多设备默认共享 workspace，还是默认设备隔离后按需共享。
3. 若个别原生工具无法完整委派，哪些缺口可接受，哪些是必须继续突破的门槛。
4. 两家账号页实际可读字段分别核实；不因Codex接口更方便而改变Claude主线。
5. 首批通用模型协议与提供商；不是现在替换两家的原生登录。
6. 用户提到的 Cursor 开源项目的精确仓库，若不是已核对的官方主仓库/SDK Bridge。
7. 许可证和第三方复用；Cockpit 的非商业约束不能忽略。
8. 环境保险需哪些必须强隔离的工具、哪些宿主专用能力接受host-exposed；普通跨目录文件访问不是待批准项。
